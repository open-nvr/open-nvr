# Publishing the camera-agent stacks to GHCR — handoff doc

**Audience:** the release owner who will publish the images.
**Goal:** a user should install either agent with a **pull-only** flow — no
local `docker build`, no sibling `ai-adapter` checkout. They run the
quickstart (or `docker compose --profile … up -d`) and every image, weights
included, comes down from `ghcr.io/open-nvr/*`.

**Decision already made:** the four lite adapter images ship with **weights
baked in** (requirement from Varun). The runtime-download code stays in as a
no-op fallback — a baked file at the expected path means no download ever
runs.

## 3. Work item A — bake the weights into the four lite adapters

The repo already has the precedent: BLIP bakes its ~990 MB weights (#79)
and moondream bakes via a build `ARG`. For the lite adapters it's simpler
because `ensure_model_file` already treats a present file as final — **bake
the file at the exact default path and the runtime download becomes dead
code**. Add to each Dockerfile (before the final `COPY adapters/…`):

```dockerfile
# llamacpp/Dockerfile
RUN mkdir -p /app/models && \
    curl -fL --retry 5 -o /app/models/Qwen2.5-3B-Instruct-Q4_K_M.gguf \
      https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF/resolve/main/qwen2.5-3b-instruct-q4_k_m.gguf

# whispercpp/Dockerfile
RUN mkdir -p /app/models && \
    curl -fL --retry 5 -o /app/models/ggml-base.en.bin \
      https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-base.en.bin

# pipertts/Dockerfile  (voice + its .json config)
RUN mkdir -p /app/models && \
    curl -fL --retry 5 -o /app/models/en_US-amy-medium.onnx \
      https://huggingface.co/rhasspy/piper-voices/resolve/main/en/en_US/amy/medium/en_US-amy-medium.onnx && \
    curl -fL --retry 5 -o /app/models/en_US-amy-medium.onnx.json \
      https://huggingface.co/rhasspy/piper-voices/resolve/main/en/en_US/amy/medium/en_US-amy-medium.onnx.json

# smolvlm/Dockerfile  (model + projector)
RUN mkdir -p /app/models && \
    curl -fL --retry 5 -o /app/models/SmolVLM2-2.2B-Instruct-Q4_K_M.gguf \
      https://huggingface.co/ggml-org/SmolVLM2-2.2B-Instruct-GGUF/resolve/main/SmolVLM2-2.2B-Instruct-Q4_K_M.gguf && \
    curl -fL --retry 5 -o /app/models/mmproj-SmolVLM2-2.2B-Instruct-f16.gguf \
      https://huggingface.co/ggml-org/SmolVLM2-2.2B-Instruct-GGUF/resolve/main/mmproj-SmolVLM2-2.2B-Instruct-f16.gguf
```

(`curl` may need adding to the apt line on the slim base;
`--mount=type=cache` is pointless here — the GHA layer cache keeps the
download layer warm as long as the URL line doesn't change.)

Notes:

* **CI PR smoke:** the publish workflow's PR path builds every matrix image.
  A 2 GB download per PR build is heavy but layer-cached after the first
  run. If it's still too slow, copy moondream's conditional-`ARG` trick
  (skip the bake on PR builds, always bake on push/tag) — but then the PR
  smoke boots via runtime download instead, which the 5-minute `/health`
  poll may or may not fit. Simplest robust option: raise that poll for the
  two big adapters.
* **Compose stays as-is:** the named weight volumes in
  `docker-compose.camera-agent-lite.yml` mount over `/app/models`.
  ⚠️ A volume mounted at `/app/models` **hides** baked files on first use —
  Docker copies image contents into a *named* volume only on first mount
  (`copy` behaviour), which does the right thing here: first boot seeds
  the volume from the baked image, no network needed. Verify this during
  the clean-machine test (step 6); if the seed doesn't happen (e.g. someone
  switches to a bind mount), either drop the volume mounts entirely (weights
  are in the image now) or keep them for upgrade-persistence — dropping
  them is the simpler call once weights are baked.

## 5. Work item C — publish the two agent app images from open-nvr

`open-nvr/.github/workflows/publish-images.yml` currently builds a single
image (`ghcr.io/open-nvr/core`). Convert the job to a matrix:

```yaml
strategy:
  fail-fast: false
  matrix:
    target:
      - { name: core,              image: ghcr.io/open-nvr/core,              dockerfile: Dockerfile }
      - { name: camera-agent,      image: ghcr.io/open-nvr/camera-agent,      dockerfile: examples/camera-agent/Dockerfile }
      - { name: camera-agent-lite, image: ghcr.io/open-nvr/camera-agent-lite, dockerfile: examples/camera-agent-lite/Dockerfile }
```

…and parameterise the `metadata-action` images, `build-push-action` file,
cache scopes, and the PR smoke step with `${{ matrix.target.* }}`. Both
example Dockerfiles already build from the repo root, so `context: .` is
unchanged. Add `examples/camera-agent/**` and `examples/camera-agent-lite/**`
to the `pull_request.paths` list.

Then flip the compose files from build-from-source to pull-first:

* `docker-compose.camera-agent.yml`: both `camera-agent` services →
  `image: ghcr.io/open-nvr/camera-agent:${AGENT_TAG:-latest}` +
  `pull_policy: missing` (keep the `build:` stanza as offline fallback).
* `docker-compose.camera-agent-lite.yml`: same for the `camera-agent-lite`
  service (the four adapters in it are already `image:` + `pull_policy:
  missing` + build fallback).

## 6. What the user experience becomes (and one nuance)

After A–C, a user needs only the open-nvr checkout (for the compose files
and quickstart script — same as Tier 0 today) plus Docker:

```bash
examples/camera-agent-lite/quickstart.sh    # or the camera-agent one
```

Compose resolves the profile and **pulls every image in it** — agent +
adapters + core, weights included. First boot goes from "build 5 images +
download 4.3 GB of models" to "pull 5 images". Nothing builds locally, and
the `../ai-adapter` sibling checkout is no longer needed.

Nuance worth knowing when explaining it: "the camera-agent image pulls its
adapters" is not literally how Docker works — an image can't pull other
images. The **compose profile** is the thing that names the full set and
pulls it. From the user's seat it looks the same (one command, everything
arrives), but if someone `docker run`s the agent image alone, no adapters
appear.
